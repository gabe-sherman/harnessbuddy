# HarnessBuddy

## What This Project Does

HarnessBuddy is a Python CLI tool that automates preparation of C/C++ libraries for
fuzzing. Given a repository URL, it:

1. Detects the build system (CMake, Meson, Autotools, Makefile).
2. Builds the library locally to validate it and collect install artifacts.
3. Probes harness compilation to discover transitive linker dependencies.
4. Generates two output directories:
   - `local/` — a standalone dev scaffold (`setup.sh`, `build_library.sh`,
     `build_harness.sh`, `harness_src/`)
   - `oss-fuzz/` — a complete OSS-Fuzz project (`project.yaml`, `Dockerfile`,
     `build.sh`, `build_library.sh`, `compile_harnesses.sh`, `harness_source/`)

When a static build fails, an optional LLM agent (`--agent claude|codex`) attempts
to repair the build script.

## Source Map

```
src/harnessbuddy/
  cli.py                        # CLI entry point and top-level pipeline
  core/
    repos.py                    # repo ingestion (URL clone, local path)
    subprocesses.py             # streaming subprocess runner
    paths.py                    # state dir and workspace paths
    reporting.py                 # Phase/PhaseReporter/FailureDiagnostic — phase start/end
                                  # banners and failure diagnostics for generate's console
                                  # output (specs/012-clear-build-logging)
  library_builder/
    models.py                   # shared dataclasses (AnalysisResult, BuildExplorationResult, ...)
    analysis.py                 # static build-system and language detection
    exploration.py              # host-side build execution and artifact validation
    scripts.py                  # per-build-system build_library.sh templates
    agents.py                   # LLM agent fallback orchestration
    harness_explorer.py         # harness compilation probe (--whole-archive dep discovery)
    environments/
      verification.py           # VerificationResult + run_local_verification/run_docker_verification
                                 # wrappers around agents/scripts/check_*_build.sh
    local/generation.py         # local output scaffold generation
    oss_fuzz/
      workspace.py               # shared Dockerfile/build.sh/project.yaml writers, used both
                                  # during exploration (workspace materialization) and by
                                  # oss_fuzz/generation.py (final output)
      generation.py               # OSS-Fuzz project generation
```

`agents/scripts/check_local_build.sh` and `check_docker_build.sh` are invoked both by the
repair agent and directly by `LocalExecutor`/`OssFuzzExecutor` (via
`library_builder/environments/verification.py`) — they are the single definition of "the
build passed" for each environment, not agent-only helper scripts.

## Key Commands

```bash
uv run harnessbuddy generate <REPO_URL>                # full pipeline
uv run harnessbuddy generate <REPO_URL> --agent claude # with LLM fallback
uv run pytest -q                                       # run tests
uv run ruff check                                      # lint
uv run ty check                                        # type check
```

## Development Standards

- Runtime: Python 3.13, managed with `uv`.
- Lint: `ruff check` — zero warnings required.
- Types: `ty check` — zero errors required.
- Tests: `pytest -q` from repo root. `tests/library_builder/test_library_build.py` is one
  of the most important test files in the repo — unlike `test_cli.py` (which mocks the
  build/executor boundaries), it exercises HarnessBuddy's actual library-build and
  harness-compile logic (`LocalExecutor`/`OssFuzzExecutor`) against real libraries and real
  build systems, so it's the primary signal that the core build logic still works, not
  just that the CLI is wired correctly. By default `pytest -q` runs its `smoke` subset — 5
  real libraries (zlib, lz4, libplist, file, lcms), round-robin split across
  `LocalExecutor` and `OssFuzzExecutor` — so it needs network access, cmake/make/
  autotools/meson on `PATH`, and a reachable Docker daemon, and takes real minutes rather
  than seconds. The rest of the static matrix (libtiff, hdf5, gpac) is opt-in via
  `-m build_matrix`; agentic libraries (c-ares, curl, tinysparql, rauc, `-m agentic`,
  invokes a live LLM agent) and `docker`-marked tests elsewhere stay opt-in too.
- All shell scripts generated by this tool must use `set -euo pipefail`.
- No relative imports (`..` paths) — absolute imports only.
- `bear` (https://github.com/rizsotto/Bear) must be installed on the local host
  (`apt install bear` / `brew install bear`) to capture `compile_commands.json` for
  Make/Autotools builds during the library-build verification stage. Best-effort on the
  local host — if missing, capture is skipped and reported, not a build failure. Always
  present in the oss-fuzz probe image, which HarnessBuddy provisions itself.
- After a major revision to build-system detection, verification/executor logic,
  generation output, or agent orchestration, run the ground-truth check:
  `uv run python tests/run_ground_truth.py` (requires Docker). It is the only check that
  exercises the full pipeline against real repositories with nothing mocked — confirm it
  reports every library passed before considering the work done. See
  `plans/ground_truth_test_modeling.md` for the plan to ground `tests/test_cli.py`'s
  fixtures in its output.
- See `plans/python_code_standards.md` for full standards.

**Note:** `.beads/`, `.claude/`, and `specs/` are gitignored — they hold local
issue-tracker state, editor/agent settings, and spec-kit planning docs, not shipped
project code. Don't stage, commit, or push them; the session-close protocol below still
applies to actual code/doc changes, just not these directories.
