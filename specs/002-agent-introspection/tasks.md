# Tasks: Agent Run Introspection

**Input**: Design documents from `specs/002-agent-introspection/`
(`plan.md`, `research.md`, `data-model.md`, `contracts/agent-run-report.md`,
`quickstart.md`)

**Tests**: Included — Constitution Principle IV requires behavior coverage for new
capability and error paths, and this project's existing agent tests
(`tests/library_builder/test_agents.py`) already establish the mocking pattern to extend.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: Maps to `spec.md` user stories (US1 = live readable narration, US2 =
  duration/cost summary + persisted report). Setup/Foundational/Polish tasks carry no
  story label.

## Path Conventions

Single project: `src/harnessbuddy/`, `tests/` at repository root (already in place — no
new top-level directories needed beyond `tests/fixtures/agent_streams/`).

## Dependencies & Execution Order

- **Phase 1 (Setup)**: No dependencies — start immediately.
- **Phase 2 (Foundational)**: No dependency on Phase 1's fixture files, but must
  complete before Phase 3/4 (both stories consume `AgentActivityEvent`/`AgentStreamResult`
  and the new model fields).
- **Phase 3 (US1)**: Depends on Phase 1 (fixtures) and Phase 2 (types). Fully
  self-contained otherwise — deliverable as a standalone MVP.
- **Phase 4 (US2)**: Depends on Phase 3 (`run_agent_streaming` and the
  `invoke_*_agent` call sites it modifies must exist first — T019-T022 edit the same
  functions T009-T013 introduced). Not safely parallelizable with Phase 3.
- **Phase 5 (Polish)**: Depends on Phases 3 and 4 both being complete.

### Parallel Opportunities

- T001, T002, T003 (different fixture files) — fully parallel.
- T007 and T008 (different test functions, same new file — safe to write in parallel,
  sequential to commit).
- T012 and T013 (same file, non-overlapping functions) can be developed in parallel but
  land as one commit given the file overlap.
- T015, T016, T017, T018 (different test files/functions) — parallel.
- T009 and T010 touch the same new file but are independent functions — parallelizable
  if the file is scaffolded first (T006), but simplest done sequentially given the small
  size of each.

## Implementation Strategy

### MVP First (User Story 1 Only)

1. Complete Phase 1: Setup (fixtures).
2. Complete Phase 2: Foundational (model fields + new dataclasses).
3. Complete Phase 3: User Story 1 — readable live narration replaces raw passthrough.
4. **STOP and VALIDATE**: run `generate --agent claude` against a known-failing build and
   confirm the terminal reads as narration, not JSON. All existing tests still pass.
5. Ship as MVP — duration/cost reporting (US2) can land in a follow-up change.

### Incremental Delivery

1. Setup + Foundational → shared types ready.
2. Add User Story 1 → validate independently → this alone already fixes the "stream-json
   is not easy to read" complaint.
3. Add User Story 2 → validate independently → adds the "agent time"/"agent cost"
   tracking on top, without touching US1's rendering logic again except for the
   `cost_usd` field left `None` there.

### Recommended order

Sequential: Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5. Unlike a typical
multi-story feature, US2's implementation tasks directly edit the same functions US1's
tasks just finished (`invoke_library_builder_agent`, `invoke_harness_builder_agent`,
`run_agent_streaming`), so the two phases are not meaningfully parallelizable across
contributors despite being independently testable checkpoints.
